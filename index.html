Flick

A Video Platform Built From The Storage Up

Flick is a small video site in the spirit of YouTube and Twitch. People can upload videos, watch them, and stream live. We build the machinery underneath it ourselves instead of renting it from a cloud company. You do not need any background in distributed systems to follow this page.

What It Does

  • People can upload a video and watch a progress bar as it goes up.
  • Videos play smoothly, because the quality drops on a weak connection instead of freezing.
  • Creators can stream live while viewers chat beside the video in real time.
  • Creators get a dashboard showing views, watch time and audience stats for each video.

The real work is the part nobody sees. Huge files have to be stored safely, converted into several qualities, and delivered to many viewers at once without the system falling over.

Why Build It

Most practice projects are a single website talking to a single database, and cloud services quietly solve the hard problems. Video does not allow that. The files are big, converting them is slow, and many people often want the same video at the same moment. Those pressures teach four skills.

  • You learn distributed systems, which means making several computers act as one and keep working when some of them break.
  • You learn systems programming, which means writing code that works directly with disks, memory and processes.
  • You learn networking, which is how data actually travels from a server to someone's phone.
  • You learn full stack development, which covers the APIs, databases and interface that people use.

Every part can be shown and measured. You can prove that a server was switched off in the middle of an upload and nothing was lost.

What Distributed Means

A distributed system is a group of computers, connected by a network, that look like one system to the people using it. You need one when a single computer cannot handle the work, or when that computer crashing would take everything down with it.

Think of a group project. If one person holds the only copy and their laptop dies, the work is gone. If three people each keep a synced copy, losing one laptop does not matter. The hard part is keeping those copies in agreement when people edit at the same time, or when someone comes back online with an old version.

Three problems come up again and again.

  • Machines fail. Disks wear out, programs crash and the power cuts out.
  • Networks are unreliable. Messages can arrive late, out of order or not at all, so a silent server might be dead or might just be slow.
  • Agreement is hard. If two servers both believe they are in charge, they can accept changes that conflict. Solving this problem is called consensus.

How The Parts Fit

Each box below is a separate program that runs in its own container. The Architecture tab shows every container in full detail.

  • The web app is the website people use. It includes the upload page, the video player, the chat and the dashboard.
  • The API gateway is the front door. Every request passes through it, and it checks who you are before sending the request on to the right service, much like a receptionist.
  • The database stores information about videos. Postgres keeps lasting facts such as users, titles and comments, while Redis keeps fast, temporary data such as who is logged in and live view counts.
  • The chunk store is our own storage system for the video files. It splits each video into pieces and keeps copies of every piece on several machines.
  • The job queue is a list of slow work waiting to be done, such as converting a new video. If a worker crashes halfway through a job, the queue gives that job to another worker.
  • The transcoders are workers that convert each upload into several qualities using a tool called FFmpeg.
  • The edge cache keeps popular pieces of video close to viewers so they load quickly, like a corner shop that stocks the bestsellers.

Life Of A Video

  1. The browser uploads the file in small pieces. If the connection drops, only the last piece has to be sent again. The database notes that the video is uploading.
  2. The chunk store splits the file into equal pieces called chunks, each about 4 MB, and writes every chunk to three machines. Small pieces are easier to copy, check and spread out than one giant file.
  3. A conversion job goes onto the queue. A worker picks it up and makes renditions, which are copies of the video at 1080p, 720p and 360p. Each rendition is cut into segments that are two to six seconds long. This is the slowest step, so it runs in the background.
  4. Segments that people watch are kept in the edge cache for the next viewer. When the cache is full, it removes whatever has gone unused for the longest time. This rule is called LRU, short for least recently used.
  5. The player downloads segments one at a time and picks the best quality the connection can handle at that moment.

Smooth Playback

Bitrate is the amount of data a video uses each second, and higher quality means more data. Every video is stored at several qualities and cut into short segments, and the player chooses a quality for each segment. This approach is called adaptive bitrate streaming, and HLS and DASH are the two standard ways of doing it.

Surviving Failure

Replication means keeping copies of the same data on several machines. To decide which copy is correct, the machines follow Raft. Raft is a consensus algorithm, which is a set of rules that keeps the machines in agreement.

Picture three friends keeping score in a shared book. One reads each score aloud, and a score becomes official once two of them have written it down. A friend who steps out copies what they missed when they return. If the reader leaves, the other two pick a new one.

Raft relies on a majority because any two majorities of the same group always share at least one member. If the network splits in two, only one side can have a majority, so only one side can make decisions. This prevents split brain, a failure where two leaders accept changes that conflict.

Where It Runs

There is no single server. Each box in the diagram above is its own small server program written in Go. A web server called Nginx sits in front, receiving traffic from browsers and passing each request to the right container.

For now, every part runs as a Docker container on your own PC. Each container behaves like a small separate machine, and one command, docker compose up, starts the whole system. Running three storage containers gives real Raft behaviour, and stopping one with docker stop node2 simulates a machine dying.

Later, if you want, the same containers can move to three to five cheap cloud servers from companies such as Hetzner or DigitalOcean, at around $5 a month each. Spare laptops or Raspberry Pis work too. This proves the system holds up across machines that are truly separate.

Running everything on one PC has three limits.

  • Containers on one machine talk to each other almost instantly. Tools such as tc and Toxiproxy can add delays and dropped messages to imitate a real network.
  • If the PC dies, every node dies with it. That is fine for learning, but it is not true fault tolerance.
  • All the containers share one processor and one disk, so speed tests will not match a real cluster.

Tools

  • Go runs the storage, the workers and the APIs. It is simple to learn, fast, and good at doing many things at once.
  • FFmpeg converts and slices video. It is free and is the industry standard.
  • PostgreSQL is the main database. It stores structured data reliably.
  • Redis is the fast cache. It keeps data in memory, so reads take microseconds.
  • React builds the website. It is the most widely used library for interactive pages.
  • WebSockets carry the live chat. They keep a connection open, so messages arrive instantly.
  • Nginx is the front web server. It is very fast at serving files and directing traffic.
  • Docker runs everything. It packages each part so the whole system starts with one command.
  • Prometheus and Grafana handle monitoring. They collect and chart response times and error rates.

All Containers

Everything inside the dashed outline runs on your PC through Docker Compose. Orange outlines mark the containers we write ourselves, and grey outlines mark ready made software.

What Each Container Does

Flick runs fourteen containers. We write nine of them in Go and use ready made software for the other five. The React website is not a container of its own, because Nginx serves its files.

Entry

  • Nginx is the only container the browser talks to, on port 80. It serves the built React files, passes API and chat traffic to the API gateway, and passes video requests to the edge cache. It is ready made.
  • Live Ingest accepts a live stream from OBS on port 1935. It runs FFmpeg on the incoming feed and writes a new segment to the chunk store every few seconds. We write it.

Services

  • API Gateway handles uploads, video details, playlists and chat. It saves records in Postgres and Redis, sends uploaded chunks to the chunk store, and adds conversion jobs to the queue. We write it.
  • Job Queue holds conversion jobs and hands each one to a single worker. If a worker goes quiet, the job goes back on the list. When too many jobs are waiting, it refuses new ones until the line shrinks. We write it.
  • Worker 1 and Worker 2 are two copies of the same program, each with FFmpeg installed. A worker claims a job, reads the original video from the chunk store, converts it, and writes the segments back. Adding more copies converts more videos at once. We write them.
  • Edge Cache keeps recently watched segments in memory. When a segment is missing, it fetches it from the chunk store and keeps a copy for the next viewer. We write it.

Data

  • Postgres stores users, videos, comments, and the list of chunks that make up each file. It is ready made.
  • Redis stores live view counts, and it passes chat messages between copies of the API gateway. It is ready made.

Storage

  • Node 1, Node 2 and Node 3 are three copies of the same storage program. Each one saves chunks as files on its own Docker volume. Raft makes one of them the leader. The leader accepts every write, copies it to the other two, and keeps the map of which node holds which chunk. If the leader stops, the other two elect a new one. We write them.

Monitoring

  • Prometheus collects numbers such as request counts and error rates from every container every few seconds. It is ready made.
  • Grafana turns those numbers into live charts. It is ready made.

Uploading A Video

Read each diagram from top to bottom. Each column is a container, and each arrow is one message between two of them. Dashed arrows are replies.

  1. The browser sends the video in small pieces to Nginx.
  2. Nginx passes each piece to the API gateway.
  3. The API gateway sends the chunks to the leader of the chunk store.
  4. The chunk store replies once a majority of nodes have saved each chunk.
  5. The API gateway records the new video in Postgres with the status set to processing.
  6. The API gateway adds a conversion job to the queue, and the browser is told the upload is done.
  7. The queue hands the job to whichever worker is free.
  8. The worker reads the original video back from the chunk store.
  9. The worker converts it into three qualities and writes every segment to the chunk store.
  10. The worker sets the video's status to ready in Postgres, and it appears on the site.

Watching A Video

Watching never downloads the whole video at once. The player fetches a playlist first, then pulls short segments one after another, mostly from the edge cache. The map below shows that path through the containers. Each number matches a step in the list further down.

The timeline below shows the same nine steps in order, from top to bottom.

  1. The viewer opens a video page, and the browser asks Nginx for it.
  2. Nginx asks the API gateway for the video's playlist.
  3. The API gateway looks up the video in Postgres to find its qualities and segments.
  4. The playlist goes back to the browser. It lists every segment address for each quality.
  5. The player asks Nginx for the first segment at the quality it thinks the connection can handle.
  6. Nginx passes the request to the edge cache.
  7. If the cache does not have that segment, it fetches it from any storage node that holds a copy.
  8. The storage node sends the segment back, and the cache keeps a copy for the next viewer.
  9. The cache sends the segment to the browser, and it plays. If the cache already had the segment, steps 7 and 8 are skipped, which is why popular videos load fastest.

Streaming Live

  1. OBS on the streamer's computer sends a constant video feed to the live ingest container.
  2. Live ingest converts the feed as it arrives and writes a new segment to the chunk store every few seconds. It also adds that segment to the live playlist.
  3. Each viewer's player asks for the live playlist every few seconds, through Nginx and the edge cache.
  4. The cache fetches the newest segments from the chunk store.
  5. The chunk store sends them back.
  6. The cache passes them to the player. Viewers end up a few seconds behind the streamer.
  7. When a viewer sends a chat message, it travels over an open WebSocket connection to the API gateway.
  8. The gateway publishes the message through Redis, so every copy of the gateway receives it and sends it to all of its connected viewers at once.

When the stream ends, its segments are already in the chunk store, so it becomes a normal video that anyone can watch later.

  1. Do the phases in order. Each one builds on the last, and the hard distributed parts only make sense once the simple version works.
  2. Finish every phase by passing its checks under Done When. If a check fails, fix it before moving on.
  3. Commit to Git each time something new works. That way you can always go back to the last good version.
  4. Keep a short notes file of what broke and how you fixed it. Those stories are the best material for interviews.

We use Go for every service we write. It is easier to learn than Rust, it compiles quickly, and its standard library already includes a web server.

Phase 0

Set Up Your Machine

The goal is to have every tool installed and working before you write any code.

Steps

  1. Install Docker Desktop. Check that it works by running docker run hello-world.
  2. Install Go from go.dev. Check it with go version.
  3. Install the LTS version of Node.js, which you need for the React website. Check it with node --version.
  4. Install FFmpeg. Check it with ffmpeg -version. The workers will run their own copy inside a container, but a local copy makes testing easier.
  5. Install a code editor such as VS Code, along with its Go extension.
  6. Open the flick repository and create the empty folders shown in the Architecture tab.

Done When

  • All four check commands print a version number without errors.

Phase 1

A Plain Video Site

The goal is a normal full stack app where you can upload a video and play it back. There is nothing distributed yet. You will learn how a React page talks to an API and how Docker Compose runs several containers together.

Steps

  1. Write docker-compose.yml with a single Postgres service, using the example below as a starting point. Start it with docker compose up.
  2. Create the Go API in api/. Begin with one endpoint, /health, that replies with ok. Give it a Dockerfile and add it to Compose.
  3. Create a videos table in Postgres with an ID, a title, a status and the upload time.
  4. Add an upload endpoint. It saves the file into a folder on a Docker volume and adds a row to the table.
  5. Add an endpoint that lists all videos and another that sends a video file back.
  6. Create the React website in web/ using Vite. Build an upload form and a page that lists videos and plays them with the standard HTML video tag.
  7. Add Nginx to Compose. It serves the built React files and passes every request that starts with /api to the Go API.
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: flick
    volumes:
      - dbdata:/var/lib/postgresql/data
  api:
    build: ./api
    environment:
      DATABASE_URL: postgres://postgres:flick@db:5432/postgres
    volumes:
      - uploads:/data
    depends_on:
      - db
  nginx:
    image: nginx:1.27
    ports:
      - "80:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/conf.d/default.conf
      - ./web/dist:/usr/share/nginx/html
    depends_on:
      - api
volumes:
  dbdata:
  uploads:

Done When

  • You can open localhost in the browser, upload an MP4, see it in the list, and play it.
  • After you stop and restart Docker Compose, the videos are still there.

Phase 2

Background Conversion

The goal is to move slow video conversion out of the upload request and into a queue with workers. You will learn why slow work belongs in the background and how a queue survives crashes.

Steps

  1. Write the job queue in queue/. Keep the jobs in memory at first. Give it three endpoints, one to add a job, one to claim the next job, and one to mark a job as done.
  2. When a worker claims a job, record the time. If the job is not marked done within a few minutes, put it back on the list so another worker can take it. This is how retries work.
  3. Write the worker in worker/. It loops forever, claiming a job, running FFmpeg to make a 720p copy, and then marking the job as done. Base its Docker image on one that includes FFmpeg.
  4. Change the upload endpoint so it saves the file, adds a job, and replies straight away with the status set to processing.
  5. Have the worker set the status to ready in Postgres when it finishes. Show the status next to each video in React.
  6. Save the queue's jobs to Postgres so that restarting the queue loses nothing.
  7. Set a limit on how many jobs may wait. When the limit is reached, the API tells the uploader to try again later. This is called backpressure.

Done When

  • Uploads finish instantly, and the status changes from processing to ready on its own.
  • Running docker compose up --scale worker=2 converts two videos at the same time.
  • Stopping a worker halfway through a job causes the other worker to finish it.

Phase 3

Adaptive Streaming

The goal is smooth playback that changes quality with the viewer's connection. You will learn how HLS playlists and segments work and how a player switches between qualities.

Steps

  1. Run FFmpeg by hand on one video to make the 720p version as HLS segments, using the command below. Then repeat it with 1080 and 360 in place of 720.
  2. Open the playlist files in a text editor. They are plain text lists of segment names, which makes HLS easy to understand.
  3. Write a master playlist by hand that points to the three quality playlists, as shown below.
  4. Move these commands into the worker so every upload produces all three qualities and the master playlist.
  5. Serve the output folder through Nginx.
  6. In React, replace the plain video tag with the hls.js library, which handles the quality switching for you.
ffmpeg -i input.mp4 -vf scale=-2:720 -c:v libx264 -preset veryfast -c:a aac \
  -force_key_frames "expr:gte(t,n_forced*4)" \
  -hls_time 4 -hls_playlist_type vod \
  -hls_segment_filename "720p_%03d.ts" 720p.m3u8
#EXTM3U
#EXT-X-STREAM-INF:BANDWIDTH=5000000,RESOLUTION=1920x1080
1080p.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=2800000,RESOLUTION=1280x720
720p.m3u8
#EXT-X-STREAM-INF:BANDWIDTH=800000,RESOLUTION=640x360
360p.m3u8

The force key frames option makes every quality cut its segments at exactly the same moments, so the player can switch between them cleanly.

Done When

  • In Chrome DevTools, setting the network speed to Slow 4G makes the quality drop without the video stopping.
  • Setting it back to no throttling makes the quality climb again.

Phase 4

Your Own Storage

The goal is to replace the single shared folder with your own chunk store spread across three nodes. You will learn how files are split, checked and copied.

Steps

  1. Write one storage node in storage/. It has two endpoints, one that saves a chunk under an ID and one that returns it. Chunks are plain files on the node's disk.
  2. Save a checksum with every chunk and verify it on every read, so damaged data is caught instead of served.
  3. Write a small Go package that the API and the workers share. It splits a file into 4 MB chunks, sends each one to storage, and records the list of chunk IDs for that file in Postgres.
  4. Switch uploads and worker output to use the chunk store instead of the shared folder.
  5. Run three storage nodes in Compose, each with its own volume. Have the shared package write every chunk to all three and read from whichever one answers first.

Done When

  • Every video still plays after you stop any one node with docker stop.
  • You have written down what goes wrong when a stopped node comes back having missed some writes. Phase 5 fixes exactly this problem.

Phase 5

Consensus With Raft

The goal is for the three nodes to always agree on which chunks exist and where, even while nodes fail. This is the heart of the project and the longest phase. You will learn leader election, log replication and majorities.

Steps

  1. Learn Raft before writing any code. Start with the animated guide at thesecretlivesofdata.com/raft, then read the Raft paper, which is short and written to be easy to follow.
  2. Add the hashicorp/raft library to the storage node. Writing Raft from scratch is a great later challenge, and MIT course 6.5840 has labs that guide you through it, but a proven library lets you focus on the system first.
  3. Store the chunk map, which records which nodes hold each chunk, in the Raft log so every node keeps an identical copy.
  4. Send all writes to the leader. If a follower receives a write, it replies with the leader's address so the client can try again there.
  5. Add a repair loop to the leader. Every few seconds it looks for chunks with fewer than three healthy copies and copies them to another node.
  6. Write a chaos script that stops and restarts random storage containers while uploads keep running.

Done When

  • Stopping the leader leads to a new leader within a few seconds, and uploads carry on.
  • A node that restarts catches up on everything it missed.
  • The chaos script runs for ten minutes and no chunk is lost.

Phase 6

Edge Cache

The goal is to serve popular segments quickly without asking the storage nodes every time. You will learn caching, the LRU rule and hit rates.

Steps

  1. Write the cache in cache/. When a segment is requested, it checks memory first. On a miss, it fetches the segment from the chunk store and keeps a copy.
  2. Build the LRU rule with a map and a doubly linked list. The map finds a segment instantly, and the list keeps track of which one was used least recently.
  3. Give the cache a size limit, such as 500 MB, and remove the least recently used segments when it is full.
  4. Point Nginx's video route at the cache instead of straight at storage.
  5. Count hits and misses so you can see how well the cache works.

Done When

  • Watching a video a second time is served almost entirely from the cache.
  • The cache reports its hit rate.

Phase 7

Live Streaming And Chat

The goal is to let a creator stream live from OBS while viewers chat in real time. You will learn how live video differs from uploaded video and how WebSockets work.

Steps

  1. Write the live ingest service in ingest/. To begin, it can start FFmpeg listening for a stream on port 1935, using the command below.
  2. In OBS, set the server to rtmp://localhost:1935/live and the stream key to stream, then start streaming.
  3. Have live ingest write each new segment to the chunk store and keep the live playlist up to date.
  4. Add a WebSocket endpoint to the API gateway for chat. Use Redis publish and subscribe so a message reaches viewers on every copy of the gateway.
  5. In React, add a live page with the player and a chat box beside it.
ffmpeg -listen 1 -i rtmp://0.0.0.0:1935/live/stream \
  -c:v libx264 -preset veryfast -c:a aac \
  -f hls -hls_time 4 -hls_list_size 6 live.m3u8

Done When

  • You can stream from OBS and watch in the browser roughly ten seconds behind.
  • A chat message sent in one browser window appears instantly in another.
  • After the stream ends, it can be watched again as a normal video.

Phase 8

Dashboards And Monitoring

The goal is to see what the system is doing at every moment and to give creators their stats. You will learn how real teams watch their systems.

Steps

  1. Add a /metrics endpoint to every Go service using the Prometheus client library. Count requests and errors, and time how long each request takes.
  2. Add Prometheus and Grafana to Compose, and point Prometheus at every container.
  3. Build a Grafana dashboard showing request rate, error rate, queue length, cache hit rate and the health of each storage node.
  4. Count views in Redis as they happen, and copy the totals to Postgres every minute.
  5. Build the creator dashboard in React, showing views and watch time for each video.

Done When

  • While the chaos script runs, Grafana shows each failure and recovery as it happens.
  • A creator can open their dashboard and see up to date numbers.

Phase 9, Optional

Real Machines

The goal is to prove Flick works across computers that are truly separate. You will learn what changes when the network is real.

Steps

  1. Rent three small cloud servers, or set up spare laptops or Raspberry Pis, and install Docker on each one.
  2. Run one storage node on each machine, and point the nodes at each other's addresses instead of container names.
  3. Before moving, test on your PC with Toxiproxy or tc to add delays and dropped messages, so you can see how the system behaves on a slow network.
  4. Run the chaos script again, this time switching off whole machines.

Done When

  • Turning off an entire machine leaves the site running and loses no videos.
